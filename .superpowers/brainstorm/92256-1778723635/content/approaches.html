Architecture Approaches

Three ways to structure the auth and data layer — pick what feels right

A

Full Supabase ⭐ Recommended

Users: Google OAuth via Supabase Auth
Admin: Email/password user in Supabase Auth with is_admin flag
Files: Supabase Storage
Data access: Row Level Security (RLS) policies on all tables

Pros

  • Single unified auth system
  • Built-in session management everywhere
  • RLS enforces access at DB level — hard to bypass
  • No custom server code needed

Cons

  • RLS policies require careful setup
  • Admin user must be provisioned once in Supabase dashboard
B

Supabase DB/Storage + Custom Admin Auth

Users: Google OAuth via Supabase Auth
Admin: Credentials stored in .env, validated via Next.js API route, session stored in a cookie
Files: Supabase Storage
Data access: No RLS — API routes enforce authorization explicitly

Pros

  • Admin auth is simple and explicit
  • Easier to reason about — no RLS complexity
  • No Supabase dashboard provisioning needed

Cons

  • Needs Next.js API routes (server code in a CSR app)
  • No RLS means authorization relies entirely on API layer
  • Two separate auth systems to maintain
C

Supabase + Separate Admin App

Users: Google OAuth via Supabase Auth
Admin: Completely separate Next.js route group or subdomain with its own auth
Files: Supabase Storage
Data access: Supabase service key used only in admin routes

Pros

  • Clear separation between user and admin surfaces
  • Admin uses service key — full DB access without RLS

Cons

  • More complex project structure
  • Service key exposure risk if not handled carefully
  • Overkill for a single admin
